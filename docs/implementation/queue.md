# 连续录音队列实现检查点

范围对应 #26：复用现有录音入口，实现同次运行的主请求槽位、开始序、严格 FIFO 上屏和逐段人工处置。依赖 #24 的原生权限／真实 BYOK 门禁仍未关闭；本检查点不宣称整票实机验收完成。

## 核心行为

- `startRecording` 不依赖网络槽位。录音状态仍只使用 ready／requestingMicrophone／recording，`finishRecording`、`cancelCurrentRecording` 和 `onChange` 与快捷键控制器兼容。
- 新片段开始时先在加密 `recording-order.enc` 原子预留单调序号；同时间戳、系统时钟回退和已删历史都不改变新片段的开始序。旧格式没有序号的未终结历史保守排在新片段前，按旧时间及 UUID 固定展示，不自动派发；无法还原旧格式同时间戳的真实开始序。
- 主池默认并发 3，设置只接受整数 1–10。降低限制不取消已有请求，后续派发等待占用降到限制以下。`mainRequestBudget.acquire(for:)`／`release` 是转写和后续润色共用的槽位；本片段没有实现润色请求或带教。
- 转写实际派发时才加载服务、模型、凭据和整体截止。等槽位没有计入请求超时。失败、超时和结果保存失败要求显式重试，旧 attempt ID 的回调不能覆盖新尝试或已取消片段。
- 文本先存为 waiting，不直接写回。队头的失败、待配置、待手动和写回不确定均阻塞后段；只有成功交付、确认本段已在外部粘贴、跳过、取消或删除队头才释放顺序门禁。复制不放行，后段不能绕过队头手动插入／确认。
- 原生 TextEdit 交付只对同控件、同窗口、相同原始文本指纹和光标快照的有效等待目标，更新已验证系统插入后的快照。AX 编辑通知仅在有限时间与次数内、且符合验证后的文本及光标状态时归因。焦点变化、用户键盘／鼠标输入、不能匹配的编辑通知仍使目标失效。实际 AX 通知次序与原生交付尚待实机验证。
- 逐段取消会取消实际 URLSession 任务，保留已有音频与文本并释放该段门禁；快捷取消仍只丢弃正在录音的片段。跳过主交付也保留历史。

## 默认背压与持久化

主积压默认 20 段、30 分钟和 256 MiB 音频。正在录音计入段数、时长和实际加密音频文件占用；请求槽位满时仍可采集。触顶拒绝新录音，录音中到达时长／音频额度时仅接受可保存部分、自动结束并保留可解码音频。主终结释放主占用，历史文件仍占默认 5 GiB 全本地额度；真实磁盘余量检查沿用现有实现。

活动音频每块先写加密音频，再更新加密 `draft.enc`，保存片段 ID、开始时间、开始序号、采样率、可靠帧数、块数和 recording 阶段。已提交历史保存开始序、队列阶段、转写状态和 attempt ID／service／model。外部写回前先持久化 delivery uncertain，成功终态保存失败时不会再次自动插入。重启后本片段不会自动发送已有请求或自动交付旧结果；旧在途显示 interrupted，旧结果要求手动交付。

完整可配置背压、离线／时间窗策略由 #29 后续接入；恢复清单与读取活动检查点由 #30 后续接入。当前不保证恢复未提交的活动音频或未落盘尾部。

## App 接线接口

`QueueWindowController(model:)` 是独立 AppKit 窗口，包含逐段状态／原因、请求并发 1–10、重试／复制／手动插入／外部粘贴确认／跳过／取消。`present()` 显示队列，`refresh()` 应从 App 的既有 `render`／`onChange` 路径调用。手动操作使用不抢键盘焦点的独立面板。

App 菜单现提供“录音队列…”入口。`AppDelegate` 懒创建并持有一个使用同一录音模型的 `QueueWindowController`；主动菜单操作调用 `present()`，既有 `model.onChange → render()` 路径调用 `refresh()`。后台刷新不显示或激活队列窗口，不另外创建录音／转写实例。窗口的真实操作矩阵仍由主线统一验收。

## 审查后的退出与重试修复

独立审查复现：只读历史目录使显式重试的 waitingForSlot 落盘失败时，旧实现已提前清除 storageFailure 覆盖层。现先成功持久化，再更新自动派发资格和清除覆盖层；失败保留原错误与恢复资格，修复目录权限不会自动重试。

公开同步 `prepareForTermination()` 用独立退出状态立即阻断新录音、主派发及自动交付，递增录音 generation 使排队授权失效，并停止已有处理。对已开始的采集只停止来源，后续 `finishRecording()` 仍正常保存可靠音频，不设置丢弃标志；音频保持 waitingForSlot 且未派发，等待后续显式恢复。一般 `stopProcessing()` 没有永久退出语义。

修复检查：只读目录重试覆盖层场景先失败 4 项后通过；仅停止处理的授权测试两种 grant 顺序均会启动采集，完成同步退出守护后均为 0 次采集、空历史和 0 POST。新增退出保存 4000 帧可解码 prefix／0 新 POST、真实 HTTP 完成后的旧结果不复活与后段不派发，以及普通停止处理后仍可再录音／请求。focused 队列检查 20 tests exit 0；全套 72 tests／4 suites exit 0；release 构建 exit 0。上述检查仍是生成 PCM、本机受控 HTTP 和真实 WAV／历史边界，实机权限与硬件门禁未执行。

## 录音热路径的音频占用缓存

独立 Debug／Release 探针确认：仅两段 597.33 秒、86,016,000 字节合法积压，每块两次 `queueUsage()` 都枚举并 stat 全部待处理音频，足以让与生产相同的 16 格录音流缓冲溢出。独立单变量对照只缓存不可变片段占用后保留全部 491,520 帧；本树 6f 基线再次复现，只保留 86,016 帧。

`EncryptedHistory` 现在按片段 ID 缓存真实音频文件占用。旧记录首次读取一次；新活动录音从空目录开始，每块用原子写入前后的实际分配增量更新；提交只移动相同文件并保留缓存。删除、丢弃或写入失败先失效相关缓存，下一次读取重新核验，不将失败当作零占用。写入返回实测 footprint，并保护减法和溢出；刷新 URL 资源属性，无法读取可靠大小或遇到非普通文件时明确失败。数据密钥、加密格式和额度数值保持既有规则。

实际验证：同一 7000 块密文积压／16 缓冲／120×4096 帧／48k 节拍，Debug 与 Release 各一次完整保存 491,520 帧，WAV 可解码且 983,040 字节 PCM 与生成输入一致，首块通过 AES 认证。另三项公开容量检查通过：活动增长／提交、录完取消与删除后的主占用和保留历史的全本地占用、录中取消后下一次分配，以及真实删除失败后仍按实际音频分配触顶。

完整 Debug 回归按分区执行：已单独通过的性能用例 1 项，加 `swift test --skip allowedPendingAudioKeepsEveryFrameFromTheBoundedCaptureStream` 的其余 75 项／4 suites，均 exit 0，共覆盖 76 项；Release 性能命令 exit 0，同时完成 release 构建。避免重复相同节拍采样。临时测试目录自动清理，保留命令、原始失败及对照日志。上述证据证明受控来源的热路径与数据结果，仍不代表真实采集、TCC 或 P95 门禁通过。
